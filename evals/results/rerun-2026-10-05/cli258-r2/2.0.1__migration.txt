A backfill is the process of writing a value into the new column for every row that already exists in the table. When you add a NOT NULL column without a default, the database must update every existing row before it can enforce the constraint, which locks the table for the entire duration on most databases.

The standard safe approach for large tables is to split the migration into three separate steps. First, add the column as nullable with no constraint. Second, run an UPDATE in batches (for example, 10,000 rows at a time) to fill in the value, so you hold locks only briefly per batch. Third, once every row has a value, add the NOT NULL constraint.

On Postgres 11 and later you can also add a column with a constant DEFAULT and NOT NULL in one statement: the database stores the default at the catalog level and avoids a full table rewrite until you UPDATE a row. If your database supports this, it is the fastest path.

If the migration is hanging right now, you must kill it before it rolls back and releases the lock, because a partial rollback on a 20 GB table takes as long as the forward run. Check for blocking queries with `SELECT * FROM pg_stat_activity WHERE wait_event_type = 'Lock'` on Postgres, then decide with your DBA whether to let it finish or cancel it.

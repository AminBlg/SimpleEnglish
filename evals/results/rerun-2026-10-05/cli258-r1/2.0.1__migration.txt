A backfill is a one-time operation that writes a value into every existing row for the new column, because the database cannot satisfy the NOT NULL constraint on rows that were inserted before the column existed.

When you add a NOT NULL column without a default, Postgres must update every row before it can enforce the constraint, and it holds an ACCESS EXCLUSIVE lock on the table for the entire duration. On a 20 GB table that lock can last minutes and block all reads and writes.

The safe pattern is three separate migrations. First, add the column as nullable with no constraint. Second, backfill in batches — run UPDATE in loops of roughly 1,000 to 10,000 rows, committing after each batch, so the lock is held only for milliseconds at a time. Third, once every row has a value, add the NOT NULL constraint using ALTER TABLE ... SET NOT NULL, which on Postgres 12 and later can be done with a CHECK constraint marked NOT VALID followed by VALIDATE CONSTRAINT, which reads but does not lock for writes.

The batch UPDATE looks like this:

```sql
DO $$
DECLARE
  last_id BIGINT := 0;
BEGIN
  LOOP
    UPDATE your_table
    SET    new_column = 'your_default_value'
    WHERE  id > last_id
      AND  id <= last_id + 5000
      AND  new_column IS NULL;
    EXIT WHEN NOT FOUND;
    last_id := last_id + 5000;
    PERFORM pg_sleep(0.05);
  END LOOP;
END $$;
```

The `pg_sleep` call gives other queries a window between batches. Adjust the batch size down if replication lag rises during the run.
